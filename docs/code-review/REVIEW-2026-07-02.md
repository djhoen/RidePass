## P1 — High: money, security, legal-record integrity

### Payments / ledger
4. **Direct-charge refunds corrupt the ledger.** `PurchaseController.cs:1601-1616` — `stripe_direct` refunds hit the platform branch (`net = -refundCents, cut = 0`), but the direct SALE row wrote `net = 0`, leaving a permanent negative available-balance for money the platform never held; the returned application fee is never reversed in `RidepassCutCents`, over-stating platform revenue. Fix: for `stripe_direct` mirror the sale row (`cut = -(prorated app fee), net = 0`).
5. **Gift-card-fully-covered sales ledger $0, underpaying the tenant.** `PurchaseController.cs:781/1684`, `SeasonPassController.cs:309` — `InsertZeroLedger` is correct for voucher-free carts but wrong when a gift card fully covers a sale (tenant credited $0 for real value); a later refund then writes `net = -refundCents`, double-debiting. Fix: ledger real gross with normal net math when a gift card covers; keep $0 only for vouchers.
6. **Gift cards have no webhook-miss fallback.** `PendingPurchaseRepository.ListStalePendingPaymentIntents` excludes `gift_card` and waitlist prepays, and there's no `stripe_connected_account_id` snapshot on `gift_card`. A missed/late webhook (notably direct mode, whose Connect webhook isn't registered in prod yet) leaves the buyer charged and the card `pending` forever — unspendable, never delivered. Fix: add gift-card + waitlist branches to the reconciler and a connected-account snapshot column.
7. **`ConfirmIntent` is broken for direct-charge tenants.** `PaymentController.cs:123` calls `GetPaymentIntentStatusAsync` with no connected account; a direct-mode PI lives on the connected account, so the platform-key GET 404s → null → no finalize. Direct-mode buyers always wait for the (currently unregistered) Connect webhook or the 20-min reconciler. Fix: resolve the connected-account snapshot by PI and pass it through.
8. **Card-present "test" endpoint mints arbitrary money with no ledger row.** `CounterController.cs:964-1017` — any `SalesCounter` user creates a live card-present PI for any amount ≥50c (`sale_kind=card_present_test`); on success the finalizer writes nothing, so the money is invisible to sales/refunds/reconciliation. Flagged independently by auth, purchase, and payments reviewers. Fix: super-admin/test-mode gate or remove before the mobile app ships.
9. **Refunds-by-worker report misses direct-mode card refunds.** `TenantLedgerRepository.cs:68-69` filters `payment_method IN ('stripe','stripe_connect')`; nothing writes `stripe_connect`, while direct refunds carry `stripe_direct`. Worker card refunds at direct-charge tenants vanish from the anti-skim report. Fix: filter `('stripe','stripe_direct')`.

### Security / auth
10. **Manager-PIN uniqueness check is an unthrottled PIN oracle.** `ConcessionController.cs:673` + `ManagerPinService.IsPinAvailableAsync` — `SetManagerPin` has no rate limit and the "Another manager already uses that PIN" response confirms a hit, letting a rogue manager enumerate the 4-digit space and impersonate a colleague's comp/void approvals — defeating the exact attribution the new lockout protects. Also the lockout increment is non-atomic read-modify-write, so parallel `CreateSale` PIN checks (not rate-limited) amortize it. Both auth and concession reviewers flagged this. Fix: apply the `manager-pin` policy to `SetManagerPin` and the sale path; atomic `failed_count = failed_count + 1 ... RETURNING`.
11. **SVG branding upload = stored XSS, reachable cross-tenant.** `TenantController.cs:29` allowlists `image/svg+xml`; in local-disk mode `UseStaticFiles` serves `/uploads/{anyTenantId}/x.svg` same-origin on every subdomain before tenant resolution. Tenant-A admin uploads a scripted SVG, phishes tenant-B users with the URL, script runs on tenant-B's origin and lifts the localStorage JWT. Fix: drop SVG from the branding allowlist (all other upload surfaces are png/jpg/webp only).

### Purchase / redemption / legal records
12. **Check-in waiver gate keys on the purchaser, not the rider.** `WaiverCheckInGate.cs:75-78` checks the purchaser's signature, but unified checkout stores each rider's signature on `event_ticket_purchase.waiver_signature_data_url` with no signature row. A buyer who once signed can pass unsigned riders (including minors) through the gate; conversely a guest buyer's fully-registered riders can be falsely blocked. `RedemptionController.Redeem` also never checks `RegistrationComplete`. Fix: honor the per-ticket rider signature and block rider-audience tickets with `registration_complete = false`.
13. **Batch admit skips server-side validation.** `RedemptionController.cs:107-170` (`AdmitBatch`) flips paid→redeemed with no waiver gate, no event-window check, and a client-supplied `AdmittedAtUtc` stored unvalidated as the legal redemption time; the roster it syncs from carries no waiver state, so the client can't have gated it either. Fix: enforce the event window server-side, clamp `AdmittedAtUtc`, and re-run the gate.
14. **Admin check-in resurrects refunded/cancelled tickets.** `ReportsController.cs:330` → `MarkRedeemed` (unconditional, no `AND status='paid'`) flips a refunded ticket to `redeemed`; toggling off calls `UndoRedeemed` → back to `paid`, making a refunded ticket sellable/refundable again. Same shape for season-pass `UpdateReservationStatus`. Fix: add status preconditions (use the existing `TryMarkRedeemed`).
15. **Minor/parent-guardian capture is client-side only in unified registration.** `PurchaseController.cs:999-1044` (`CompleteTicketRegistration`) never checks `WaiverPolicy.IsMinor`; blank/minor DOB is accepted with no guardian, while the counter path enforces both. Confirmed no server validation. Verified independently by rider-frontend and purchase reviewers. Fix: mirror the counter check server-side.
16. **Anonymous re-registration overwrites completed/checked-in tickets.** `EventTicketPurchaseRepository.cs:238-254` has no `registration_complete=false`/status guard, so any ticket-GUID holder can overwrite rider identity, birthdate, waiver signature, and emergency contact after check-in; `WaiverSignatureDataUrl` is unvalidated and unbounded (multi-MB strings stored). Fix: only allow re-registration while `pending/paid` and not complete; validate the signature data URL.

### Rider-facing checkout
17. **Failed Stripe redirect payments are shown as success.** `FinishRegistration.vue` (mount ~line 179) never reads `redirect_status`/`payment_intent`, and the backend serves/completes registration for `pending` tickets, so a rider whose 3DS challenge fails signs the waiver and sees "You're all set for the gate," then is denied. The same missing-`redirect_status` handling recurs in `BuyGiftCard.vue`, `BuySeasonPass.vue`, `Rentals.vue`, `WaitlistConfirm.vue` (only `Membership.vue` does it right), inviting double-purchases. Fix: read redirect params on the landing/return path and confirm the intent (Membership.vue pattern).

### Admin
18. **Post-success refresh failure reports money actions as failed.** `SuperAdmin/Payouts.vue:344-383` — `sendPayoutViaStripe` awaits `refreshDetailDialog()` inside the try; a refresh 500 flashes "Stripe transfer failed" over the success and leaves the row pending, so the super admin clicks Send again. Transfer idempotency (`payout-{id}`) now dedupes the actual Stripe call, so this is a UX/data-integrity trap rather than a double-spend, but it reads as a failed transfer. Fix: move refresh awaits outside the try (or give them their own catch).

Same fix pattern as the other read-then-write races.
- **SendGrid webhook can poison-loop on a stale tenant id.** `SendGridEventService.HandleAsync` passes the event's `tenant_id` custom arg straight into `email_suppression.tenant_id` (`REFERENCES tenant(id)`); an event for a deleted tenant throws an FK violation, the batch returns non-2xx, and SendGrid retries the identical batch indefinitely. ### Coverage note
All nine reviewers reported (the data-layer sweep ran ~48 min). Its isolation sweep traced every id-only `WHERE id = @id` write in the repos changed since May (waitlist, campaign, survey, rental, loampass, event-subscription, reward, cash) and found **no new cross-tenant read/write leak** — each is guarded by a tenant-scoped fetch, an ownership check, or an unguessable capability token before the id-only write. `v_recent_sales` (Script0145) covers all seven live sale kinds and is in sync. Email/code case handling is consistently `lower()`-both-sides or `ILIKE` (no half-lowered `col LIKE LOWER(@p)` instances); all money in 0100+ is integer cents; all new timestamp columns are `timestamptz`; new tenant-scoped tables carry tenant-leading indexes. The isolation model (subdomain → middleware → policy handler cross-check) holds across the reviewed surface; the remaining risk is breadth (a sale kind or charge mode a cross-cutting check missed), not the core architecture.
