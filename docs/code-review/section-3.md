# Section 3: Schema, migrations & data integrity

This section is pure schema review — every migration under `RidePass.Migrator/Scripts/` was read top to
bottom and the live shape they produce was cross-checked against the rules listed in
`.claude/skills/tenant-audit/SKILL.md`. No `dotnet build`, no `psql`, no controller code.

## Scope

Files read end-to-end (80 migrations; 0037 is intentionally skipped):
- `Script0001_InitialSchema.sql` through `Script0080_RecentSalesView.sql` in numeric order
- Inline trigger functions: `set_updated_at`, `ensure_tenant_branding`, `seed_default_event_types`,
  `seed_initial_waiver`, `seed_default_extra_products`, `seed_default_pass_products`
- `v_recent_sales` (Script0080)
- `.claude/skills/tenant-audit/SKILL.md` (per-tenant table list cross-checked against the schema)

Spot checks via Grep:
- Every `REFERENCES users(id)` to verify ON DELETE policy
- Every `purchaser_user_id` / `*_by_user_id` for FK consistency
- Every `updated_at` column for trigger coverage
- `set_updated_at` trigger creations

## Architecture summary

**Layout.** Single Postgres schema (`public`). All PKs are `uuid`. The schema is snake_case throughout
and uses `timestamptz` for everything time-shaped. Money is `int` (cents) everywhere — no `numeric` or
`float` columns sneak in. Multi-tenancy is enforced at the row level by `tenant_id uuid NOT NULL
REFERENCES tenant(id) ON DELETE CASCADE` on every per-tenant table; users are split into globally-scoped
(`super_admin`, `rider`) and tenant-scoped (`tenant_admin` and the four staff roles), enforced by
`chk_user_tenant_scope` on `users`.

**Identifiers.** `tenant.subdomain` is the public addressing dimension and is globally `UNIQUE`. User
emails are unique per tenant for staff (`idx_users_email_per_tenant`, partial unique
`WHERE tenant_id IS NOT NULL`) and globally unique for super admins and riders
(`idx_users_email_super_admin`, partial unique `WHERE tenant_id IS NULL`). Coupon and gift-card codes
are `(tenant_id, lower(code))` unique. Stripe `payment_intent_id` lookups are filtered (where `IS NOT
NULL`) and most are non-unique indexes (a single PI can fan out to several purchase rows, e.g. the
counter cart in Script0015).

**Audit / append-only / idempotency.** The ledger (`tenant_ledger_entry`) is append-only with three
filtered unique indexes on `(tenant_id, source_kind, source_id)` — one each for `entry_kind = 'sale'`,
`'dispute_loss'`, `'dispute_fee'` — so webhook retries can't double-write. Section 2 flagged that rental
sales are not yet ledgered; the schema is fine, the wiring is missing. `audit_log` uses `ON DELETE SET
NULL` for both `actor_user_id` and `tenant_id`, so audit rows survive both user and tenant deletion.

**Trigger surface.** One generic `set_updated_at()` PL/pgSQL function is reused by ~25 `BEFORE UPDATE`
triggers. Tenant-insert triggers seed: `tenant_branding`, six (MX) or two (MTB) default event types,
an initial waiver placeholder, a "Day Pass" placeholder pass_product, and four default extra products
(Gate Fee, Camping, Parking, Pit Vehicle). All seeds use `ON CONFLICT DO NOTHING` (except
`seed_default_pass_products` and `seed_default_extra_products`, which use `WHERE NOT EXISTS` guards in
their backfill blocks) so re-running is safe. The event-type and waiver seeds branch on
`tenant_type` (Script0078).

**The day_pass → pass rename.** Script0056 introduced a refactor that was journalled before its body
ran (a stray `BEGIN/COMMIT` collided with DbUp's per-script transaction). Script0057 is the idempotent
retry; Script0062 cleans up a leftover `dispute.day_pass_purchase_id` column the rename missed. The
result is correct but the journey is visible in the diff — see "Patterns worth replicating" below.

**Waiver evolution.** The `rider_waiver_signature` table accumulated columns over six migrations
(0005, 0023, 0031, 0067, 0068, 0069, 0071) as the product moved from "one waiver per tenant, signed by
a registered rider" to "many waivers per tenant, signed by anyone for anyone, with separate
spectator/racer versions per event." The resulting shape is busy but coherent; the only structural
problem is the `ON DELETE CASCADE` from signature to waiver (see Finding 3).

**v_recent_sales.** Script0080 introduces a single read view that UNION-ALLs the seven purchase tables
(`pass_purchase`, `event_ticket_purchase`, `event_extra_purchase`, `season_pass_purchase`,
`membership_purchase`, `gift_card`, `rental_purchase`) into a normalized seven-column shape. Joins to
parent product tables for `item_name` are all LEFT JOIN so a sale survives product deletion.

## Patterns worth replicating

1. **Filtered partial unique indexes for idempotency.** The ledger table's three `UNIQUE INDEX (tenant_id, source_kind, source_id) WHERE entry_kind = 'X'` indexes (Script0016/0017/0018) are textbook. They let webhook retries race without double-writing and they avoid penalizing legitimate same-source rows of different kinds. The same pattern is reused on `gift_card_redemption.uk_gift_card_redemption_source` and `coupon_redemption.uk_coupon_redemption_source` (with the noted scope caveat).

2. **Snapshot-at-purchase columns.** `daily_rate_cents_frozen`, `unit_price_cents_frozen`, `name_at_purchase`, `price_cents` on `membership_purchase`, `size_at_purchase`/`color_at_purchase`/`gender_at_purchase` — every purchase that references a mutable product carries a frozen snapshot. Refunds and historical reports stay correct even after the tenant edits the product. This is consistent across passes, rentals, extras, memberships, and season passes.

3. **Tenant-insert seed triggers with idempotent backfill.** Every "this tenant needs default rows" requirement uses the same shape: a `seed_*` PL/pgSQL function fired by `AFTER INSERT ON tenant` plus a one-time backfill SELECT/INSERT with `WHERE NOT EXISTS` (or `ON CONFLICT DO NOTHING`). Adding a new default in a new migration just needs to extend the function and re-backfill — see Script0067's Gate Fee addition as the canonical example.

4. **Branch-on-tenant_type for product variants.** Script0078 introduced `tenant.tenant_type` and immediately taught the three seed triggers (`seed_default_event_types`, `seed_initial_waiver`, `seed_default_pass_products`) to branch on it. This keeps MX vs. MTB venue defaults sane without forking the schema. The pattern scales to BMX, equestrian, etc. — just extend the CHECK and the IF branches.

5. **Half-applied migration recovery.** The Script0056 → Script0057 "rename retry" is exactly the right way to recover from a journalled-but-not-committed migration: leave the broken script in place (so its journal entry stays), write a new idempotent script that converges from either state. The retry uses `IF EXISTS` / `DROP CONSTRAINT IF EXISTS` everywhere and would no-op if 0056 had run successfully on a fresh DB.

6. **Filtered indexes for sparse columns.** Every nullable Stripe PI column has a filtered index (`WHERE stripe_payment_intent_id IS NOT NULL`), keeping the index small for the very common "look up by PI" path. Same pattern for `redemption_token`, `gift_card_pending_delivery`, `event_waiver_id`, etc. — uniformly applied, never bloated.

7. **Append-only ledger model.** `tenant_ledger_entry` is never UPDATEd — corrections are net-negative `'refund'` or `'adjustment'` rows. The schema enforces this implicitly (no UPDATE trigger; the column shape encourages new rows). This is the right shape for a financial ledger and the controller code respects it.

## Open questions

1. **Why is `season_pass_purchase.purchaser_user_id` CASCADE while every other purchase table is RESTRICT or SET NULL?** This is almost certainly an oversight rather than a design choice. Worth a fix before any rider self-delete flow ships.

2. **Was `coupon.issued_from_purchase_id` deliberately FK-less?** The comment hints at FK semantics ("can render them under My Passes filtered by the source purchase") but the migration just declares it as `uuid NULL`. May be a deferred decision because the issuing path crosses table boundaries (bundled-coupon mint happens in the webhook).

3. **Should the `tenant-audit` skill's table list be authoritative or descriptive?** Several entries don't match the schema as built (`event_type` doesn't exist — it's `tenant_event_type`; `newsletter_campaign` and `newsletter_recipient` should be `email_campaign` and `email_campaign_send`; `notification_preference` has no tenant scope; `event_subscription` is per-tenant despite being listed as global). The skill should be updated, or the schema should grow `tenant_id` columns to match.

4. **Why does `tenant_waiver` have a partial unique index removed (Script0067) with no replacement?** Allowing multiple active waivers is the intended new behavior, but nothing prevents two waivers with the same `name` from existing simultaneously. If the application UI doesn't enforce uniqueness, admins will hit confusing fall-through behavior when no explicit waiver is attached to an event.

5. **Should `membership_purchase` carry a `redemption_token`?** Every other purchase table has one. If memberships are meant to be QR-redeemable in the future, adding it now is a one-line column with default `uuid_generate_v4()` and a unique index — vs. a backfill later when there's data.

6. **Is `v_recent_sales` performance-tested?** Seven UNION ALLs each scanning a purchase table is fine while volumes are small, but PG won't push status filters down through the view cleanly. If the admin dashboard ever shows "recent sales" without a date predicate at scale, this view will full-scan every table. Materialized view or a status-filtered base query is the lever to pull.
